## 5. 模型与动作（这部分最容易踩坑）

### 模型

B站 **@是依七哒** 的「秋千版」昔涟。**Cubism 5.0**（`.moc3` 头 `4D 4F 43 33 05`）。

⚠️ **授权要求：注明用途 + 不得收费。** 署名在 `NOTICE.md` 第四节，**改代码时别删**。
⚠️ **模型文件不入库**（`*.moc3` / `*.motion3.json` / `*.exp3.json` / `assets/live2d/` 都在 gitignore）。

### 原始模型有三处必须修（`tools/fix-live2d-model.mjs` 可重放）

1. **`model3.json` 没挂 `Motions` / `Expressions`** —— 不改的话 4 个动作 + 13 个表情**一个都不加载**
2. **`LipSync` 分组是空的** —— 补 `ParamMouthOpenY`
3. **纹理 8192×8192** —— 降到 2048（8.4 MB → 0.9 MB）

> ⚠️ 降采样**不能直接 resize**：该纹理是直通 alpha，且 5680 万个透明像素里存了垃圾 RGB。
> 直接四通道重采样会把垃圾颜色插值进边缘 → **黑边**（实测 24.5% 边缘像素差异 > 120）。
> 正确做法 **预乘 → LANCZOS → 反预乘**，见 `tools/downsample-texture.py`。

### 四个动作（名字都是 `SceneN`，内容是反推出来的）

| 动作 | 时长 | 内容 | 独有参数 |
|---|---|---|---|
| `Scene[0]` | 3s | **比嘘手势**（半眯眼 wink，手指举到唇边 / 用户看画面描述为"一只手放在下巴处握拳"） | `Param15 嘻嘻` `Param5 星星` `Param12 手指` |
| `Scene[1]` | 4s | **叉腰 + 星光**（闭眼笑） | `Param7 闪耀` `Param17/18 叉腰1/2` |
| `Scene[2]` | 3s | **招牌姿势 + 张嘴说话 + 甩头** | `Param10/11 招牌1/2` `嘴开闭` |
| `Scene[3]` | 180s | **荡秋千**（长期待机用） | `Param13/14 秋千` `Param31/32` 腿鞋摇晃 |

**反推方法**：`PET_SAMPLE_PARAMS=1` 采样各动作驱动的参数（免费又精确，比逐帧截图强）。

### 状态 → 动作映射（`live2d.js` 的 `STATE_MAP`）

| 状态 | 动作 | 表情 | 备注 |
|---|---|---|---|
| `idle` | Scene[3] 荡秋千 | reset | 180s 长循环 |
| `running` | **不播动作**（`motion: null`） | reset | + `Param9 思考` → 保持"一只手放下巴"的思考姿势。**为什么不用动作**：`Scene[0]` 内含"右手比嘘"且循环 → 干活时一遍遍比嘘（"很聒噪"）；荡秋千 + `Param9` → 秋千占两只手、Param9 又加一只手 = **三只手**（用户截图）。自测锁住 |
| `approval` | Scene[1] **只播一次** | surprise | `keepEffect: true`（特效留着，表达"还在等你"） |
| `question` | Scene[2] | question | 循环，要一直等回答 |
| `done` | Scene[1] **只播一次** | happy | 演完**特效也撤**（用户要求） |
| `error` | Scene[3] | reset | ⚠️ 模型**没有**"困扰"参数，靠 `ERROR_FACE` 手工凑眉毛 |

### 三条特殊规则

1. **开场手势**：启动先演一次 `Scene[0]` 比嘘，**0.6x 慢放**，演完落待机。
   期间到达的状态**排队等它演完**（只有 `approval`/`error` 能打断）。
2. **眨眼**：库的自动眨眼只在"没有动作播放"时才跑。所以只有 **Scene[3]（只在前 2.2s 驱动眼睛）需要我们自己兜底眨眼**；
   Scene[0]/[1]/[2] 全程驱动眼睛，**让它们自己演**（Scene[0] 是个 wink，强行睁眼会毁掉表情）。
3. **循环开关是双向的**：Scene[0] 既当开场手势（只播一次）又当 `running`（要循环），
   `setMotionLoop(index, loop)` 必须显式设成 true/false，不能只关不开。

### ✅ P1：A6「双击派活 / 打断」—— **已于 2026-10-02 确认可用**

用户原话："测试成功了，可以打断。"

**但它不是"没测过"，而是连撞了五个 bug**（每修掉一层才露出下一层）：

**① 500 `cannot get property "agents" without inject`**

- **根因**：Cordis 的 ctx 是 Proxy —— 访问一个**已注册的服务**属性时，若该名字不在插件的
  `inject` 列表里就**抛错**，而不是返回 undefined。而当时 `inject` 只声明了 `webServer`。
  于是 `resolveAgent()` 里那句 `agents === undefined` 的兜底**根本执行不到**。
- **修法**：`inject = ['webServer', 'agents']`。
- **它为什么能躲过自测**：mock ctx 把 `agents` 当普通属性发，没复现 inject 校验
  → 又是"mock 比真实宿主宽松，测出假象"。已把 mock 收紧成 Proxy，并补静态扫描 + 负向对照。
  反向验证：把 `inject` 改回 `['webServer']` → **失败 6 项**（含 4 条真 `/prompt`、`/interrupt` 路由）。

**② 修完变 503 `取不到 @deepseek-ai/dsh-llm 的 createUserMessage`**

- **根因**：插件是**从仓库目录按路径挂载**的，而 `@deepseek-ai/dsh-llm` 只存在于
  **宿主自己的应用包内**（`app.asar/dsh/node_modules/@deepseek-ai/dsh-llm`）。
  裸包名解析只从**插件自己所在目录**往上找 → 必然 `ERR_MODULE_NOT_FOUND`。
  这不是环境偶然：**任何要从宿主包里拿东西的外部插件都会踩**。
- **修法**：两条腿走路 ——
  1. 尽力取**官方工厂**：`config` 注入 → 裸包名 → 用 `process.resourcesPath` 拼出
     `app.asar/dsh/node_modules/…` 的绝对路径（含 `app.asar.unpacked` 变体）；
  2. 全失败时用 `makeUserMessage` **内置等价实现**兜底，**不再返回 503**。
- **为什么敢自己造**（下面每条都从 asar 里读出来核实过，不是猜）：
  `createUserMessage(input)` = `createMessage({ ...input, role: 'user' })`；
  `createMessage(input)` = `deepFreeze(structuredClone({ ...input, id: brandString(randomUUID()) }))`；
  而 `brandString(v)` 的实现就是 `return v` —— `@deepseek-ai/dsh-brand` 自述
  "Duplicate-install-safe … keeps no runtime identity or mutable state … independently
  installed copies produce interchangeable values"，即它只是**编译期**标记。
  所以官方产物 == `{ ...input, role: 'user', id: <v4 uuid> }` 的深拷贝 + 深冻结，可逐字复刻。
- **诊断入口**：`/health` 新增 `messageFactory`（`config` / `module:<路径>` / `builtin`）
  和 `messageFactoryAttempts`（各候选的失败原因），一眼看出走的哪条路。
**③ 又变 503 `ctx.agents.get(sessionId) 不可用或 sessionId 缺失`**

- **根因**：渲染端只在 SSE `snapshot` 帧里学 sessionId，而 **DSH 刚重启时 `/state` 是空的** ——
  窗口"**先连上、会话后出现**"，于是它手上的 `latestSessionId` 一直是 `undefined`，派活必失败。
  （`/state` 的 `seq` 只有 1，正好印证"插件几乎还没见过事件时窗口就连上了"。）
- **顺带核实**：`ctx.agents` 注册表**是以 sessionId 为键**的 —— typert 的 agent lookup 写着
  `wireTypeSymbol: dsh-session/types#SessionId`、`resolve: (sessionId) => this.get(sessionId)`。
  所以键没问题，问题在"根本没传 id"。
- **修法（服务端兜底，不指望客户端状态）**：`/prompt`、`/interrupt` 在渲染端没给 id
  （或给的 id 已失效）时，由**插件自己**退到 `primarySessionId(state)` —— 最近活跃的会话。
  另外每一帧都带上 `primarySessionId`，渲染端随便哪一帧都能学会。
- **为什么用"最近活跃"而不是状态优先级**：`done` 的优先级(3)高于 `running`(1)，
  按优先级挑会挑到一个早已结束的会话 —— 等于把活派给死会话。新增 `lastActivityAt` 打点，
  活跃时间打平时才用优先级兜底。
- **诊断**：503 正文现在带 `requestedSessionId` / `triedSessionIds` / `knownSessions` / `reason`。

**④ 还是 503 `no-agent` —— 而这次 sessionId 完全正确**

- **现场证据**：`/state` 里 `primarySessionId` 就是那个活跃会话的 id，兜底候选没问题；
  但 `ctx.agents.get(那个 id)` 返回 `undefined`。
- **根因**：`ctx.agents` 的注册表实现是
  `get(id) { return this.store.get(id)?.agent }`，而 `store` 只放 **entered（活着）** 的条目
  （`detachEntered()` 一 detach 就 `store.delete`）。所以**会话不活跃时必然拿不到 agent** ——
  sessionId 对不对根本不影响。这也解释了为什么 code 6 那轮"能过"：那一次 agent 恰好是活的。
- **正解**：走 **`ctx.sessionController.agents.resolveAgent(sessionId)`**。类注释写着
  `Owns every operation that may create, resume, or configure a Web Agent`，
  方法注释写着 `Resolve or resume one ordinary Session, deduplicating concurrent resumes`，
  返回 `{ agent }` 或 `{ error }`。
  **GUI 提交消息走的正是这条** —— 宿主把 typert 的 'agent' lookup 换成了它
  （`lookups.configure('agent', … resolveAgent …)`）。
  所以插件现在的策略是：先试活 agent（快路径），再让 `resolveAgent` 解析/恢复。
  另需在 `inject` 里加上 `sessionController`（否则读属性就抛，见 ①）。
- **诊断**：503 正文带 `reason`（`no-session-known` / `not-resolvable`）、
  `triedSessionIds`、`knownSessions`、`resolveErrors`，消息里也带上 reason。

**⑤ 变成 503 `no-session-known` —— 气泡里现在会带 reason 了**

- **现场证据**：`/state` 里 `primarySessionId` 有值、`sessions` 非空，`code=9` 已加载；

- **根因**：插件"知道有哪些会话"**完全来自它自己观测到的事件**。DSH 刚重启时它一个都没观测到，

### ✅ token 口径 + 清未读（2026-10-03，**都要重启 DSH**）

**① token 口径改对了（原来那个数字是错的）**

实测 `/state` 报过 **33,929,445（3390 万）** tokens。根因：把每次 `assistant/message` 的
`usage.totalTokens` **直接累加**，而 `totalTokens` 里含 `cacheReadTokens` ——
那是**整个上下文被重发**的部分。真实载荷（从 DSH 落盘的会话日志里挖出来，zstd 逐帧解压）：

```json
{ "inputTokens": 664, "outputTokens": 153, "cacheReadTokens": 9600,
  "cacheWriteTokens": 0, "totalTokens": 10417 }
```

664 是新输入，9600 是重发的上下文 —— 逐轮累加等于把同一段上下文数几十遍。

**改成照抄宿主 `tokenMeter`（`usage-projection.js`）的四桶口径**：

```js
{ uncachedInputTokens, outputTokens, cacheReadTokens, cacheWriteTokens }
```

- 用量 = 四桶之和；缓存命中率 = `cacheRead / (cacheRead + uncachedInput)`（本例 93.5%）
- 同一 `(turn, step)` 重复上报 → **替换**（`addReplacing`），不是累加
- `llm/retry-started` → 取消去重（重试确实又烧了一次）

⚠️ 踩坑：`llm/retry-started` **不在 `EVENT_STATE` 里**，第一版把处理分支写在状态映射之后，
被 `target === undefined` 提前 return → 静默变死代码。**测试抓到了**，现已移到映射之前，
并留了一条专门覆盖它的断言。

**② 清未读（原来点了没反应，坏了两层）**

- **第一层**：`markRead()` 是**死代码** —— `mousedown` 无条件 `dragging = true`，
  `mouseup` 里 `if (!dragging)` 永远不成立。也就是说"单击清未读"从来没生效过。
- **第二层**：就算执行到，它也只 `setBadge(0)` 清**本地显示**，没告诉插件；
  插件的会话 `unread` 还是 true，下一个 `state` 帧就把 `unread: N` 报回来 → 徽标复原。

修法：
- 插件加 **`POST /read`**（`markRead(state, sessionId?)`，清完推一帧 `state` 出去）
- 渲染端修好"点 vs 拖"：按下记坐标，位移 ≤ 4px 才算单击（拖拽手感不变，仍按下就告知主进程）
- 单击角色 **和** 点右下角徽标都清未读；徽标也加进了 `visibleUiRects`（否则又会被穿透）

**③ 双击暂时保留**：右键菜单还没做，取消了就没有打开派活输入条的入口了（等菜单上线再让位）。

**验证**：`node tools/check-plugin.mjs` → **89 项**。反向验证做了三次：
关掉 retry 分支 → 恰好那条失败；`addReplacing` 退化成纯累加 → 恰好去重那条失败；
去掉 `/state` 里的宿主同步 → 恰好"以宿主为准"那条失败。

**④ 数据源换成宿主的 durable projection（2026-10-03 晚，**需重启 DSH**）**

上面 ① 只是把**算法**改对了，数字仍然是**插件进程内**累加的 —— **DSH 一重启就归零**，
所以 675k 其实是"自插件启动以来"而非会话真实累计。

改成读宿主的 session projection：

```js
ctx.sessionProjections.stateOf(session, 'tokenUsage').totals   // ← 四桶，durable
```

踩到的关键细节：
- 投影内部是**以 session 对象为键的 `WeakMap`** —— 拿 `sessionId` 字符串查不到，
  必须在 `session/event` 里顺手存下宿主给的 session 对象（`sessionObjects`）
- `inject` 要加 `sessionProjections`
- 设计成**纯增强**：读不到就退回插件自算，绝不报错（`/state` 用 `tokenSource: 'host'|'own'` 标明来源）
- 刷新时机放在"**数字要被用到之前**"：`/state`、SSE snapshot、提醒引擎 tick —— 不必每事件都刷
- 切到 `host` 源后插件**不再自己累加**（否则两边混着算，数字会飘）

### ✅ 花销提醒改基线制 + 右键菜单（2026-10-03 晚，**都要重启 DSH**）

- 每 5 次巡检记一行**心跳**：`心跳 动作=Scene[N] 管理器空闲=… 状态=…`
  → 下次复现时日志能直接指出"动作何时变为空闲、当时什么状态"

实测（`PET_FORCE_STATE=idle` 跑 40 秒）：心跳稳定显示 `管理器空闲=false`、巡检未误伤开场手势 ✓

**实机验证（2026-10-05，用户确认"现在荡秋千动作开始循环了"）**

### 🐛 "长时间待机后退出待机动作"（2026-10-04，**修了两轮才真修好**）

用户报："昔涟在长时间待机之后会退出待机动作"。第一版修复后用户回"**还是会停**" ——
因为第一版只覆盖了 `idle` 分支，**没覆盖真实路径**。

**第一版的定位（对了一半）**：`setIsLoop(true)` 在这个模型上不生效。
隔离复现（`PET_FORCE_STATE=idle`）日志：
```
Scene[3] 循环=true（第 2 次尝试）                                  ← 循环"设上了"
⚠️ 非一次性动作 Scene[3] 收到 motionFinish（循环未生效）→ 重新开始   ← 180 秒后它还是结束了
```
`Scene[3]`（荡秋千）模型里时长 **180 秒** → 症状是"待机几分钟后不动"。

**真实路径（`PET_FORCE_STATE=done`，第二次复现）**：
```
状态 → done（动作 Scene[1]，只播一次）
Scene[3] 循环=true（第 2 次尝试）                     ← 实际在播的已是待机动作
⚠️ 待机动作 Scene[3] 播完（setIsLoop 未生效）→ 重开    ← 修复后 ✓
```
agent 干完活后 `currentState` 是 **`done`**（一次性状态**刻意保留**不切走 ——
未读背板要一直显示），但**实际在播的已经是待机动作**。第一版逻辑走到
`mapped.once` 为真 → `returnToBaseMotion()` → 它开头
`if (currentMotion === BASE_MOTION) return` → **直接返回、没人重开** → 停住。

**教训**：**状态与动作是两件事**。判断"刚播完的是哪个动作"必须用 `currentMotion`，
不能用 `state.currentState`。

**最终修法**：决策抽成纯函数 `renderer/motion-policy.js` 的 `decideOnMotionFinish()` ——
第一优先 `currentMotion === baseMotion` → 重开；其次 `once` → 回待机；
其余非一次性状态 → 重开自己的动作。

**为什么要抽纯函数**：这个 bug 的判据原本要"跑满 180 秒"，又慢又不可重复。
抽出来后自测能**秒级**盯住（+1 项，共 105），含"done 状态下待机动作播完必须重开"这条
（正是漏掉的那条）。反向验证：去掉第一优先判断 → 该测试**恰好失败**。

⚠️ 另一条方法论：**复现条件必须匹配真实路径**。第一版复现用强制 `idle`、
真实场景是 `done` —— 复现"看起来通过"了，实际 bug 还在。复现前先确认
"真实场景此刻究竟是什么状态"。

1. 桌宠在线（`subscribers=1`）→ 应答者**持住**了请求、没有交棒
2. 链路是**顺序**的（探针实验已证明）→ 我们持着时 **GUI 没有提示可点**
3. `rejected` 正是我们应答者返回的值

**测试方法上的一条**：拒绝路径用"**文件是否存在**"这种外部可观测的副作用当判据，
比"我觉得弹出来了"可靠得多 —— 命令没执行和"没跑成功"看起来太像。

**验证**：测试 98 → 103（默认关闭不注册；没连桌宠立刻交棒；允许→`allowed-once`
且**帧里带 callId 关联出的命令**；拒绝→`rejected`；超时→交棒且确实等了超时时间）。
抓图核对了卡片布局（命令三行截断、倒计时、两个按钮、她在下方仍可见）。

⚠️ 踩坑：审批注册最初写在 `disposers` 声明**之前** → `Cannot access 'disposers' before
initialization`（TDZ）。注册已挪到既有注册区。

### 🧪 审批能否由桌宠同意 —— 实验结论（2026-10-04）

用户问："能不能让 DSH 产生请求的时候通过桌宠同意"。先做隔离实验：探针**默认连 `ctx.on` 都不调**，
只有 `POST /debug/approval-probe {enabled:true}` 才挂上，且**永远只观察 + 永远 `next()` 交棒**，
不可能放行/拒绝任何真实操作。

**宿主机制（asar 里查到的事实）**
- `@deepseek-ai/dsh-user-approval`（组合里 `yes`）提供 `ctx.approval`
- `ApprovalService.decide()` → `ctx.waterfall(scopeTarget(agent, agent), 'approval/request', req, () => 'unavailable')`
- **fail-closed**：没人返回 `'allowed-once'` 就不放行（那是唯一的放行值）
- 包描述："dispatched to **composed answerers** over the approval/request waterfall"

**第 1 级（plain 注册）→ `seen=0`**：审批确实发生了
（真实事件 `approval/asked` seq 7333 → `approval/decided` seq 7334 `allowed-once`，用户 3.4 秒后放行），
但一次都没被调用。**不是作用域问题**（读 `scopeTarget` 过滤器：`tag === undefined → return true`，
无 scope 的监听器会被接受），而是**顺序**：链路前面是"转发给 GUI 的桥"，它 await 用户答复并返回决定，链路就此结束。

**第 2 级（`prepend: true`）→ `seen=1`** ✓ 决定性证据：
```
approval/asked    seq 7475  time 1791115959666
探针收到                     time 1791115959667   ← 只差 1ms
approval/decided  seq 7476  time 1791115960755   ← 用户约 1.1 秒后放行 allowed-once
```
且交棒后 **GUI 提示照常弹出、用户正常放行** → 交棒语义正确。

**结论：可行**。正解 `ctx.on('approval/request', fn, { prepend: true })`，自己返回 `'allowed-once'` / `'rejected'`。

**落地前必须解决**
1. **挡住 GUI**：我们"持着"时 GUI 不再弹提示 → 必须（a）桌宠没连上/功能没开就**立刻交棒**，
   （b）用户不点时**超时交棒**（否则 agent 干等、界面全空）
2. **安全**：`prepend` 让**每一次**审批都先过我们（含 shell 命令）→ 界面必须显示**工具名 + 命令 + 理由**

**命令怎么拿**（实测）：`approval/request` 只有 `agent, toolName, callId, reason, signal`，**没有命令原文**；
但 `tool/call` 事件（本来就收）带 `callId` + `name` + `arguments`（命令 JSON）→ **按 `callId` 关联**即可显示。

⚠️ **教训**：这次改了插件（探针补记 keys/sample）**忘了把 `CODE_REVISION` +1**，
`code 21` 同时对应两版代码、无法从版本号判断是否加载。**改插件必 +1。**

**验证**：自测 98 项全绿（探针两条：默认完全不注册；开启后挂 1 个应答者，且走 waterfall 后
返回的仍是 fallback `'unavailable'`，即"从不返回决定"——反向验证：改成 `return undefined` 恰好那条失败）。
实验结束后已 `POST {enabled:false}` 注销，链路恢复原样。

## 7. 关键决策记录（为什么是这样）

| 决策 | 为什么 |
|---|---|
| **插件 + 独立窗**，不做 GUI 内嵌 | 内嵌需要 client 插件 bundle（构建链 + 版本耦合）；独立窗零依赖、可独立迭代 |
| **SSE 放主进程** | 渲染端连会撞 CORS/origin；主进程连还能统一管重连 |
| **`pet://` 自定义协议**（页面 + 模型同源） | Cubism 要把 `.moc3` 读成 ArrayBuffer，走 XHR；而 **Chromium 禁止 `file://` 页面 XHR `pet://`/`file://`**。同源后 CORS 问题消失，CSP 也能收紧回 `'self'` |
| **CSP 保留 `'wasm-unsafe-eval'`、拒绝 `'unsafe-eval'`** | Cubism Core 是 wasm（需要前者）；PixiJS 需要 eval，用官方 `@pixi/unsafe-eval` 替代（不用放宽 CSP） |
| **`live2d.js` 是 ES 模块** | 两个普通 `<script>` 共享全局作用域，撞过两次（`const` 重名 → **整页静默失效**；`function` 重名 → **静默互相覆盖**）。用**动态 import** 是为了保留"失败仍能降级到占位图" |
| **`preserveDrawingBuffer: true`** | alpha 掩码要靠 `drawImage(webglCanvas)` 取样，默认 false 时在渲染循环外读到空白 |
| **命中测试放主进程轮询光标** | `setIgnoreMouseEvents(_, {forward:true})` 是 Electron 在 Windows 上的**已知 bug**（见 §8）。改用 `screen.getCursorScreenPoint()` 完全不依赖它 |
| **构图按包围盒而非画布** | 模型画布 4200×3500 里角色只占中间一块，按画布适配会显得很小 |
| **构图缓存** | 现场测量要 3 秒，期间会有一次可见的缩放跳变（用户实测报过"打开一会突然变大"） |

## 8. 踩过的坑（别重蹈覆辙）

### 环境类

| 坑 | 症状 | 解法 |
|---|---|---|
| Electron 二进制没装 | `require('electron')` 卡在 "Downloading..." | 用 `tools/fetch-electron.mjs`（华为云镜像，15 秒） |
| agent 沙箱里 Electron 起不来 | `Mojo platform_channel.cc:108 拒绝访问 0x5` | 需 `danger-full-access` 提权；日常让用户自己跑 |
| `cubism4.min.js` 引用 `process` | `ReferenceError: process is not defined` → **整包不执行** | 加载 `vendor/process-shim.js` |
| PixiJS 需要 eval | `Current environment does not allow unsafe-eval` | 加载 `@pixi/unsafe-eval` |
| `web_fetch` 工具被域名过滤 | 几乎全站 `resolves to a non-public IP` | **用 Node 的 `fetch`**，它是通的（10/10 站点可达） |

### 代码类

| 坑 | 症状 | 根因 |
|---|---|---|
| **两个 `<script>` 撞名** | 一次是 `SyntaxError` 整页失效；一次是 `function` 静默覆盖 | 共享全局作用域 → 改 ES 模块 |
| **模板字符串括号顺序笔误** | `SyntaxError: Missing } in template expression`，**肉眼看不出来** | 写成了 `` `Scene[${x]}` `` 而不是 `` `Scene[${x}]}` ``。**逐字符 hexdump 才定位到** |
| **全局环形缓冲被高频通道刷爆** | `/debug/shapes` 80 条样本全是流式帧 | 改按 channel 分别限量 |
| **循环引用载荷预览不可读** | `agent/status` 的样本文本 `<unserializable>` | 安全序列化（循环处标 `[circular]`） |
| **动作播放时库不自动眨眼** | 待机眼睛一直闭 | 条件 `if (!motionUpdated) eyeBlink...`；自己兜底 |
| **眨眼接管条件写反** | 比嘘的 wink 变成两只眼睁着 | 判据应是"哪些动作持续驱动 `ParamEyeLOpen`"（数据），不是"哪个动作闭眼"（零散现象） |
| **`motionGroups` 懒加载** | 刚调 `motion()` 时取不到 motion 对象 | 50ms × 20 次重试 |
| **外部挂载的插件 import 不到宿主的包** | `import('@deepseek-ai/dsh-llm')` 必然 `ERR_MODULE_NOT_FOUND` → 派活 503 | 裸包名只从插件**自己所在目录**往上找，该包却在宿主 `app.asar/dsh/node_modules/` 里。**实测：`file://` 指向 asar 内文件能成功 import**（Electron 44 支持），所以现在用的是官方工厂；内置等价实现只作兜底 |
| **状态只在快照里学一次** | 派活 503 `no-agent`：窗口"先连上、会话后出现"时，渲染端手上的 sessionId 永远是 undefined | 快照只是**连接那一刻**的切片 → 后续每帧都要能补齐（`primarySessionId`），且**服务端自己兜底**比指望客户端状态更稳 |
| **`ctx.agents.get()` 只找"活着的" agent** | 派活 503 `no-agent`，**而 sessionId 完全正确** | 注册表只放 entered 条目，detach 即删 → 不活跃的会话必然 undefined。要**解析或恢复**得走 `ctx.sessionController.agents.resolveAgent(id)`（GUI 提交消息也是这条） |
| **"我知道的会话"只来自自己观测的事件** | 派活 503 `no-session-known`：DSH 刚重启，插件一个会话都没观测到，空窗期候选为空 | 观测事件 ≠ 世界全貌。宿主本来就有 `ctx.sessions.list()` / `ctx.agents.list()`，**别自己攒状态去猜 —— 能问就问** |
| **命中测试只看 alpha 掩码** | 输入条右侧的「打断」点不到（穿透），而压在角色上的「派活」能点 | 掩码里只有 Live2D 像素，**HTML 控件不在其中** → 控件矩形要跟掩码一起送主进程；判定抽成 `hit-test.js` 纯函数才测得到 |
| **绝不能用 pwsh 改含中文的源码** | 注释变乱码、吞换行 | 一律用 edit/write 工具 |
| **`Invoke-RestMethod -Body <字符串>` 发中文变 `?????`** | 通知 / 派活里的中文到宿主成了问号 | PS 5.1 对字符串 body 默认 ASCII 编码 → 传**字节**（`UTF8.GetBytes`）+ `charset=utf-8` |
| **绝对定位 + `display:flex` 把中文挤成一列** | 通知条变成"一个字一行"的高柱，几乎占满 260×300 的窗口 | 绝对定位元素宽度是收缩适应，flex 文本项被压到近 0 宽 → 改**固定宽度 + 块级布局** |
| **拿 `usage.totalTokens` 累加当用量** | `/state` 报出 **3390 万** tokens | `totalTokens` 含 `cacheReadTokens`（重发的整个上下文）→ 改**四桶**分记 + 按 `(turn,step)` 增量替换（对齐宿主 `tokenMeter`） |
| **清未读"假清"** | 点了徽标不消失，或过一会儿又冒出来 | ① `markRead()` 是死代码（`mousedown` 无条件 `dragging=true`）；② 它只清本地显示、没告诉插件，下一个 `state` 帧就报回来 → 加插件端点 `POST /read` |
| **`llm/retry-started` 不在 `EVENT_STATE` 里** | 放在状态映射之后的处理分支**静默变死代码** | 会被 `target === undefined` 提前 return → 必须放在状态映射**之前**（已加专门断言） |

### 测试方法类（这几条害我差点把 bug 当修好）

| 坑 | 症状 |
|---|---|
| **测试开关和产品行为耦合** | `deferShow` 绑在 `PET_SNAPSHOT` 上 → 快照测试永远走"立即显示"分支，**真实路径从没被验证** |

## 12. 给接手者的一句话

**这个项目最大的风险不是技术，是"以为验证过了"。**

我踩过两次：一次是测试开关和产品行为耦合、一次是真实状态干扰测试，
两次都让日志看起来"通过"，实际根本没测到要验证的分支。

**所以：每个"已修复"都要有可复现的证据**（截图、参数采样区间、逐条日志），
拿不到证据就老实写"未验证"。§2 那张表就是按这个标准写的，请继续维护它。
