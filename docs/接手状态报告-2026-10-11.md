### 1.1 沙箱 / 权限边界（今天复现过的）

- **写**：工作区内自由；工作区外（`~/.dsh`、`%APPDATA%`、其它盘）被拒 → 需要时对**同一条命令**要一次

- **读工作区外是允许的**：我读了 `~/.dsh/profiles/desktop/*` 与 `F:\dsh\...` ✓

### 4.1 A7「点通知条唤回 DSH」——从"原因不明"到"根因复现 + 已修"

> 🔴 **前提变更：这整套功能在同一天被用户要求删除了**（见 §4.4）。
> 下面这一节因此**只剩"知识"价值** —— 代码已经不在了，但"为什么它会静默失败"这件事
> 仍然值得记：一是因为它是本项目"以为验证过了"的又一次重演，二是因为**能力本身是好的**，
> 将来若把"跳回 DSH"挪进右键面板，直接照这里的修法搬即可（`.cache/_extract-focus.mjs`
> 与 `_mutations.json` 还留着可复跑的证据脚本）。

**症状（历史证据）**：`.state/focus-log.txt` 10 条全 FAIL，形如
`ok=False detail=no-window pids=2 visible=0 titled=0`（最后一条 2026-10-06）。

**关键推理**：`visible=0` 是**自相矛盾**的 —— 任何时刻都有可见顶层窗口（今天实测 `visible=18~26`）。
它说明 **`EnumWindows` 的回调一次都没跑**（`cb=0`），而不是"没有符合条件的窗口"。

**真因**：脚本里那段 `Add-Type`（P/Invoke 声明，跳转实现的核心）**编译不出来**，
而 `$ErrorActionPreference='SilentlyContinue'` 把错误吞了，只剩一句误导的 `no-window`。
**为什么编译不出来**：`Add-Type` 要往 `%TEMP%` 落编译产物；桌宠是**长命进程**，
若它的 `TEMP` 是某个**已被回收的一次性目录**（DSH 沙箱给每条命令的临时目录就是这种），
PowerShell 会退化成 **ConstrainedLanguage**，`Add-Type` 直接拒绝。

**可复现证据**（把 TEMP 指向不存在的目录，跑的还是 main.js 里那段脚本）：

| 场景 | 输出 |
|---|---|
| 正常 TEMP | `ok=True ... isForeground=True title=… — DeepSeek Harness cb=408 visible=26 titled=16 lang=FullLanguage` |
| TEMP 指向不存在目录 | `ok=False detail=add-type-failed: … lang=ConstrainedLanguage cb=0` |

（历史 10 条 FAIL 的输出形态 = 第二种，只是当时没把原因打出来。）

**修了四处**（`packages/pet-shell/main.js`，都不改交互语义）：

1. 子进程显式拿到 `.state/tmp`（自己 `mkdirSync`）当 `TEMP/TMP`，不再继承可能失效的那个；
2. 失败**分类**：`add-type-failed: <原因>` 与 `no-window` 分开报，并带上 `cb/visible/titled/pids/lang`；
3. 新增 `cb=`（回调次数）—— "脚本到底跑没跑起来"一眼可读；
4. 成功判据改成**复核出来的** `GetForegroundWindow()==hwnd`，并补一手 `SwitchToThisWindow`
   —— 实测 `SetForegroundWindow` **返回 False 而窗口其实上去了**（`okApi=False switched=True isForeground=True`）。

**验证**：把 main.js 里那段脚本**原样抽出**（`.cache/_extract-focus.mjs`）后用
`powershell.exe -EncodedCommand` 跑，两种场景的输出见上表 —— **脚本侧通过**。

**当时的"还差一步"（现已作废）**：原计划是让你重启桌宠、点一次通知条确认观感。
**不用了** —— 通知条已经删掉，这一步随功能一起取消。

#### 4.9.1 托盘结论（2026-10-12，多轮实机对照）——**根因：桌宠进程跑在 Low 完整性，托盘被系统拒绝**

  **没有 `electron.exe` 的登记项**（微信/Steam 都有）。

#### 4.9.4 根因确认（2026-10-12，最小复现）

用**最小 Electron 程序**（`.cache/tray-app`，不是桌宠、没有我们的任何代码）做终局实验：

| 启动方式 | 结果 |
|---|---|
| Medium 控制台 + `--no-sandbox` | 能跑，但 **`integrity=Low(S-1-16-4096)`**，托盘 `bounds=0,0` |
| Medium 控制台 + **不带** `--no-sandbox` | **起不来**，`exit=-2147483645` = **`0x80000003`（STATUS_BREAKPOINT）** |

→ **这台机器上 Chromium 沙箱初始化失败**（0x80000003），所以 `--no-sandbox` 是必需的；
而 `--no-sandbox` 下 Electron 进程会被降到 **Low 完整性** → Windows 拒绝托盘图标。

**两个约束互相锁死**：开沙箱→起不来；关沙箱→Low→无托盘。
因此 **托盘在本机无解（应用代码层面）**，与桌宠代码、图标、启动链、权限级别**均无关**
（启动链和 Medium 环境都已用最小程序排除）。

**可行的两条修法（都不在"托盘代码"里）**：
1. **修机器环境**：排查让 Chromium 沙箱起不来的东西（Windows 安全中心「漏洞利用保护」里的
   任意代码防护 ACG / 代码完整性防护、组策略、安全软件驱动）。修好后 Electron 能以默认沙箱启动
   → 自动变 Medium → 托盘自动出现（启动器的沙箱探测会自动不再加 `--no-sandbox`）。
2. **原生托盘助手**：独立 Win32 托盘进程（PowerShell+WinForms 或小 exe），桌宠通过文件/IPC 控制。
   不依赖 Chromium 完整性，**必然能显示**；代价是发行包多一个常驻组件、多一套 IPC。
   若用户仍要托盘，走这条。

#### 4.16 大小「实机失效」的三个坑（2026-10-12，全部已修并验证）

用户实机反馈："大小设置没起作用，实际上感觉像是把角色向右下平移。"

**① 主进程改了窗口，渲染端没重排**（表因）
`live2d.js` 的 resize 监听是**节流 + 超时丢弃**：拖动滑杆会连续送来多次 resize，
最后一次被丢弃 → 模型保持旧大小/旧位置。改成**防抖**（`clearTimeout` + `setTimeout` 120ms），
保证"最后一次一定排"。自测护栏同步改成断言防抖（禁止回退成节流）。

**② 光靠 resize 事件不可靠** → 主进程主动发信号
新增 IPC `pet:relayout`（preload `onRelayout` → `pet.js` → `live2d.relayout()`），
`applyScale()` 里发两次（立即 + 300ms，覆盖视口更新延迟）；
`relayout()` 内部再补两次（200ms/600ms），因为 `layoutFromContent()` 幂等、日志按指纹去重。

**③ 真正的根因：Pixi 的 `autoDensity` 把画布内联宽高定死了**
实测日志（诊断期）：
`canvas 262×302 / stage 156×182 / body 156×182 / html 156×182 / inner 156×182`
—— 页面各层都缩到 156，**只有 canvas 还是 262**。于是模型仍按 262 的世界排布，
被 156 的窗口裁掉右下角 = "没缩放 + 像被平移"。
修法：`layoutFromContent()` 改成读 `#stage` 的尺寸，并先 `state.app.renderer.resize(cssW, cssH)`
把 Pixi 渲染器/画布同步到舞台，再算构图。

**④ 顺带修掉一个我自己引入的死循环**
`enforceWindowSize()` 严格相等比较：本机对无边框透明窗 `setBounds(260×300)` 后
`getBounds()` 报 `261×301` → "纠正→再纠正"死循环（历史日志里**同一秒最多 73 次**）。
加 **2px 容差**（仍能抓住 534×586 那种 2 倍漂移）。

**端到端验证（真实鼠标自动化，不是只测函数）**：
脚本 `.cache/probe-slider-e2e2.ps1`：起探针桌宠 → WM_CONTEXTMENU 开面板 → 网格点击 ⚙ →
设置窗打开 → 真实鼠标拖动滑杆到 0.6 → 读日志。证据链：
```
设置窗已打开
大小：0.60× → 窗口 156×180（锚底边，位置 948,524）
构图：内容 135×119 CSS px / 舞台 156×180，scale=0.0403，上方留白 55px
```
内容从 `239×207@262×302` 缩到 `135×119@156×180`（≈0.575，与 0.6 一致）→ **缩放真的生效了**。
自测 **239 项全绿**（新增 1 条护栏：重排必须读 #stage、必须 `renderer.resize`、必须有 relayout 链路）。

#### 4.17 阶段 4 第二项：不透明度（2026-10-12，已接通并验证）

**做法**：设置窗加「外观 · 不透明度」滑杆（30%–100%，步进 5%），拖动 120ms 防抖后
`settings:patch` → 主进程 `applyOpacity()`。

**关键发现：`win.setOpacity()` 在 Windows 的透明窗口上无效**。
第一版就是这么写的，日志显示 `不透明度：30%` 正常，但截屏对比桌宠区域**像素 diff 只有 0.2**（等于没变）。
改成**渲染端整体淡出**：主进程发 `pet:opacity` → `pet.js` 设 `#stage.style.opacity`
（她 + 气泡一起淡）；`win.setOpacity()` 保留为其他平台/非透明窗的兜底。
另外在 `pet:fit-ready`（渲染端就绪）时补发一次设置值 —— 启动时 `applyOpacity` 跑在渲染端加载之前，会丢。

**端到端验证（真实鼠标 + 屏幕像素）**：
脚本 `.cache/probe-opacity-e2e2.ps1`：起探针 → 先截桌宠基准图 → 右键开面板 → 点 ⚙ →
设置窗里**真实拖动不透明度滑杆到 30%** → 点「完成」关窗 → 再截桌宠 → 逐像素对比。
- 日志：`设置窗已打开` → `不透明度：30%`
- **桌宠区域平均像素差 = 12.6**（阈值 10；<1 就是没生效）
- 截图证据：`.cache/ui-mockups/opacity-before.png`（满血）vs `opacity-after.png`（30%，明显变淡）
- 途中踩过一个取证坑：设置窗会**盖住整个桌宠区域**，一开始拿被盖住的区域对比，diff 永远是 0.2 误判
  —— 改成"关窗后再截图"才是有效证据。

自测 **239 项全绿**（+2：滑杆范围与 `OPACITY_MIN/MAX` 一致；必须走渲染端而不是 setOpacity）。

#### 4.18 阶段 4 第三项：左右翻转 + 自动朝向（2026-10-12，已接通并验证）

**做法**：
- 构图变换抽成纯函数 `renderer/mirror-math.js` 的 `fitTransform(content, cssW, cssH, { mirror, marginPx, fill })`：
  镜像时 `scaleX` 取负，并且**以内容包围盒为轴**翻（`posX = dX + (content.x + content.w) * scale`），
  这样"她站的位置"不变、只是左右互换 —— 翻错方向/翻完偏移是镜像最典型的两个 bug，这里用行为断言钉死。
- 渲染端 `live2d.setMirror(bool)` 走**镜像渲染**（`model.scale.set(fit.scaleX, fit.scaleY)`），
  而不是给画布加 CSS transform：因为画布位图本身被翻，`readAlpha()` 出来的**命中掩码自动也是镜像的**，
  点击/拖拽与画面对应 —— 不需要任何额外的"翻转映射"（那才是容易出错的地方）。
- 主进程：`effectiveMirrorState()` = `autoFace ? autoMirrorState : settings.appearance.mirror`
  （自动开着时以自动为准，手动翻转不生效，UI 里那一行会变灰）；
  `maybeAutoFace()` 挂在已有的光标轮询循环里（每帧顺手判），**300ms 防抖**（用户明确要求）。
- 设置窗新增两个开关：左右翻转 / 自动朝向（珍珠白小胶囊样式，不用系统 checkbox 的蓝）。

**验证**：
- 纯函数行为断言 2 条：非镜像包围盒居中贴底；镜像后"局部左侧的点显示在右侧"、包围盒位置不变、垂直不受影响。
- 变异测试：把 `scaleX` 改成不取负 → 自测立刻红（`镜像后左变右、右变左`），恢复后全绿。
- **端到端（真实鼠标点击开关 + 截屏）**：
  - 点「左右翻转」→ 日志 `镜像：开（手动翻转）` + 渲染端 `[live2d] 镜像：开`；
  - 截图**紫色（翅膀）像素质心**：翻转前 `x=148`（图宽 327，中心 163），翻转后 `x=177.7`，
    镜像期望 `327-1-148 = 178`，**误差 0.3px** → 画面精确左右翻转了；
  - 自动朝向：光标移到她左侧 → `镜像：开（自动朝向）`；移到右侧 → `镜像：关（自动朝向）`，
    间隔约 1.2s（300ms 防抖后稳定触发，不会来回抽）。
- 自测 **239 项全绿**（+3：镜像构图 2 + 接线 1）。

**待用户确认**：方向约定「光标在她左侧 → 镜像开」是推断的（模型默认朝哪边没法从数据判断），
实机若感觉朝反了，把 `maybeAutoFace` 里的 `cursor.x < b.x + b.width / 2` 改成 `>` 即可（一行）。

#### 4.19 自动朝向的「互动死区」：靠近她时不跟随（2026-10-12，按用户要求新增）

**用户反馈**："能不能让鼠标放在昔涟附近的时候不触发镜像跟随？防止互动的时候动来动去。"

**做法**：`window-placement.js` 新增纯函数 `pointNearRect(point, rect, radius)`；
`maybeAutoFace()` 里先判死区 —— 光标落在**她窗口外扩 `AUTO_FACE_NEAR_RADIUS = 80` DIP** 内时：
- 冻结当前朝向（不翻转）；
- 取消已经攒着的待执行翻转（`autoMirrorPending = null`）；
- 日志只在"进入/离开死区"时各打一行，不刷屏。

离开死区后才恢复"稳定 300ms 再翻"的跟随逻辑。半径是一个常量，觉得 80 太近/太远改它即可。

**验证（移动真实光标 + 读日志）**：
```
光标在她左侧 40px（死区内） → 自动朝向：光标靠近她 → 暂停跟随   （没有任何 镜像： 行）
光标移到左侧 500px（死区外） → 自动朝向：光标已离开 → 恢复跟随 + 镜像：开（自动朝向）
光标移回她身上（死区内）     → 自动朝向：光标靠近她 → 暂停跟随   （没有翻回去）
```

**自测**：新增 1 条纯函数行为断言（框内、边界含、超出 1px、radius=0 退化），
`node tools/check-plugin.mjs` → **239 项全绿**。

#### 4.9.2 官方资料与下一步假设（2026-10-12 调研）

## 6. 红线（改代码前必读，违反过、都出过事）

1. **`.cmd` 文件只能有 ASCII**（注释也算）—— 非 ASCII 会被 cmd 当 GBK 解成乱码**命令**。
2. **不许用 PowerShell 写含中文的源码**（乱码 / 吞换行 / CRLF 污染 diff）—— 一律用 edit/write。
3. **观测型插件只订阅通知型事件**；订阅 `tools/pre-execute` 这类 **waterfall** 事件必须 `return next()`，
   否则**整个 profile 的每次工具调用全废**（2026-09-29 真实事故，重启 DSH 也不恢复）。
4. **改插件源码必须重启 DSH**（`hmr.root` 实测无效，ESM 缓存不失效）；
   **改外壳/渲染端只需重启桌宠**；看生效与否**只看 `/health` 的 `code`**，别看 `uptimeMs`。
5. **改 profile patch 前先备份**（`~/.dsh/profiles/desktop/cordis.patch.yml.bak-*` 已有 4 份），
   且**拒绝 `!!js`**（= 配置期代码执行）。
6. **素材与署名不许动**：`LICENSE`（必须纯 MIT 正文）、`NOTICE.md`（模型作者 @是依七哒 的用途署名
   必须保留）、`assets/live2d/`＋`packages/pet-plugin/icon.webp` 是**唯二入库的第三方素材**
   （图标是社区图、作者不明，**不许**说成"自绘/原创/官方原画"）。
7. **禁止用源码正则断言代替行为断言**（2026-10-05 的坐标 bug 就是这么被锁死的）；
   每条新逻辑配**变异测试**——绿色本身不算证据。
