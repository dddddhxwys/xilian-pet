  浏览器 F11、视频全屏（DWM 合成）通常**不**复现 —— 所以"只有原神发现"多半是因为
  你其它游戏用的是**无边框窗口**模式（那也是本问题的通用规避方式）。

## 3. 机制三选一（决定"能不能便宜地修"）

| 机制 | 特征 | 桌宠能否浮在上面 |
|---|---|---|
| ① **独占全屏**（DXGI flip exclusive） | 显示器直接归游戏，DWM 不参与合成 | ❌ **不可能**（OBS / Discord / Steam 覆盖层同样失效） |
| ② **独立翻转 / 全屏优化（FSO）** | 表面"全屏"，实际仍由 DWM 合成 | ✅ 周期性重抢 z-order 通常能回来 |
| ③ **游戏自建 topmost 窗抢走最上层** | Windows 里 topmost **是一个"带"**，带内顺序取决于"谁最后 raise" | ✅ 同上 |

**判别只要 30 行 + 一次实机测试**（见 §5），别直接上大改。

## 5. 重开时的第一步：判别实验（30 行）

目的：分清"她只是被抢了 topmost 顺序"（可修）还是"游戏独占全屏"（不可修）。

- 加一个调试开关（默认关，例：`PET_TOPMOST_DEBUG=1`）：在已有的 16ms 光标轮询里节流 2 秒，
  执行一次 `win.moveTop()` + `setAlwaysOnTop(false)` → `setAlwaysOnTop(true,'screen-saver')`，
  并把次数写进 `pet.log`。
- 用户操作：重启桌宠 → 原神 Alt+Enter 全屏 → 看 30 秒。

**判定表**（这是它能省掉后面所有猜测的原因）：

| 现象 | 结论 | 下一步 |
|---|---|---|
| 她没被盖住 | 属 ②/③ | 转方案 2（把调试版做成常态） |
| 被盖住 **且** 日志里有抢的次数 | **确诊独占全屏** | 只剩方案 0 或方案 3 |
| 被盖住 **且** 日志里没有抢的记录 | 触发条件/开关没生效 | 修触发，不换方向 |

## 6. 方案 2 的设计要点（已论证，直接可用）

**它到底解决什么**：Windows 的 topmost **不是"绝对最上"，而是一个"带"**；带内谁在上取决于
**谁最后被 raise**。方案 2 = 定期把顺序抢回来。它**不是**破解独占全屏。

**触发（三条都要）**：

| 触发 | 理由 |
|---|---|
| 周期抢，**3 秒** | 无法 hook 游戏的 raise 动作，只能定期兜底。16ms 会跟别的 topmost 应用打架；30s 主观上就是"坏了" |
| `screen.on('display-metrics-changed')` 立刻抢一次 | 游戏 Alt+Enter 常伴随分辨率/刷新率变化 → 唯一的**事件型**信号，零成本 |
| 窗口刚显示/从隐藏恢复时抢 | 供方案 3 复用 |

**关键 API 语义**（已核）：`win.moveTop()` 官方注明 *"Moves window to top(z-order) regardless of focus"*
→ **不抢焦点**，这是本方案能存在的前提（玩游戏时绝不能被桌宠抢焦点）。

**代码落点**：

- 新纯函数模块 `packages/pet-shell/topmost-policy.js`（Node 可 import → 可自测）：
  `TOPMOST_REASSERT_MS` + `shouldReassertTopmost({enabled, visible, now, lastAt})`（节流 + 开关 + 可见性）
- `main.js`：`reassertTopmost(win)` helper + 搭在已有的 16ms 轮询上 + `display-metrics-changed` 监听 + 计数日志
- 默认**开**，用 `PET_NO_TOPMOST_REASSERT=1` 关（⚠️ 本项目被 opt-in 坑过：审批 `viaPet` 原来默认关，
  导致手写安装的人静默走 GUI —— 见 commit `bbc55fe`。别再犯）

**必须处理的六个坑**：

1. **绝不抢焦点**：只用 `moveTop()`；不要 `focus()`/`show()`/`showInactive()`。
2. **辅助窗顺序**：菜单窗/审批窗是**独立窗口**，抢完必须把它们也 `moveTop()`，否则菜单被压在她下面。
3. **不碰位置/尺寸**：`setPosition`/`setSize` 在游戏切分辨率时会跟系统打架。
4. **不可见时别抢**：供方案 3 共存（否则会把藏起来的她顶出来）。
5. **节流**：3 秒，避免和录屏/悬浮窗等 topmost 应用互抢。
6. **接受白抢**（独占全屏）—— 靠**日志**把它证出来，而不是靠猜。

**成本**：~50-65 行 + 5-7 条自测（节流语义/开关/可见性）+ 3 条变异；**只需重启桌宠**；风险低。

## 7. 方案 3 的额外前提（真要做得知道这些）

- **检测必须先标定**：`SHQueryUserNotificationState()` 在本机**当前基线已经是 `QUNS_BUSY`**
  （§2 实测），不能拿它当触发器；需要先量"全屏时 / 平时"各是什么值。
  备选：`display-metrics-changed` + "前台窗口矩形 == 屏幕矩形"（Windows 枚举 —— 正是随通知条一起
  删掉的那套 `focusDshWindow` 机器，需要时可从 git 历史里取回思路）。
- **恢复入口**：现在没有托盘，只有 `Ctrl+Shift+Q`（退出）。自动隐藏必须**绝对可靠**，
  否则她"消失"了就只能重启；建议顺手加一个全局快捷键（例：`Ctrl+Shift+H` 显示/隐藏）。
- **副作用**：她真的浮在游戏上之后，**她身体那块会吃掉游戏点击**（全项目一贯的命中测试行为，
  在游戏里更明显）—— 所以"让开"和"浮着"是两个需求，别混着做。
