## 2. 【P0·已证实·**已修复**】左键分区互动的坐标系是错的

> **2026-10-05 修复状态**：已按下面的结论改完，见 §10「修复记录」。
> 坐标换算抽成纯函数 `hit-test.js/rawToLocal()`，并把原来那条"把错公式写成断言"的
> 源码正则测试换成了**行为断言** —— 已做**变异测试**验证它真的会红（见 §10）。

### 症状与真因

用户原话（`070e224` 提交信息引用）："秋千的判定还是错的，**靠下的部分一直都点不到**"。

真因不在"两边量纲不同"（那是提交信息的说法），而是 **换算公式本身两个系数都错**：

| 轴 | 代码现在用的<br/>`renderer/live2d.js:534-535` | 正确的 | 错法 |
|---|---|---|---|
| X | `(rawX+0.5) * originalWidth` = `rawX*4200+2100` | `rawX*3500+2100` | 系数**放大 1.2 倍** |
| Y | `(rawY+0.5) * originalHeight` = `rawY*3500+1750` | `-rawY*3500+1750` | **符号反了（上下镜像）** |

- `3500` = `canvasinfo.PixelsPerUnit`；`4200` = `canvasinfo.CanvasWidth`。**两者不相等**，所以 X 必然错；
  而 `CanvasHeight(3500) == PixelsPerUnit(3500)`，所以 Y 的**系数碰巧对、只有符号错** —— 这正是它看起来"只坏了一半"的原因。
- 正确式子**恰好等于库自己的 `getDrawableVertices()`**。

**后果（按实机构图 `local→window` 系数 ≈ 0.0694 换算）**：

- **Y 镜像** ⇒ 点击点的局部 y 被拿去和 `3500 - y` 处的顶点比较 ⇒ **窗口下半部分整体映射到上半部分**，偏差最大 **±200px**（窗口才 300px 高）。**这就是"靠下的部分点不到"**。
- X 拉伸 ⇒ 以屏幕 x≈127 为中心横向拉 1.2 倍，两侧最大 **±24px**，每侧翅膀外缘约 20px 变成死区。
- 等价说法：点击 `(cx, cy)` 实际是在问真实位置 `(0.8333·cx + 21.2, 382.2 − cy)`。

   ```js
   getDrawableVertices(drawIndex) {
     const arr = this.coreModel.getDrawableVertices(drawIndex).slice();
     for (let i = 0; i < arr.length; i += 2) {
       arr[i]     =  arr[i]     * this.pixelsPerUnit + this.originalWidth  / 2;   // 3500，不是 4200
       arr[i + 1] = -arr[i + 1] * this.pixelsPerUnit + this.originalHeight / 2;   // ← 有负号
   ```

### 为什么 119 项自测全绿却没发现

`tools/check-plugin.mjs:2104-2112` 这几条**不是行为测试，是对源码文本做正则匹配**：

```js
assert.match(live2d, /\(positions\[vi \* 2\] \+ 0\.5\) \* sizeW/, '顶点必须换算成局部像素再比')
assert.equal(/unitMapper/.test(live2d), false, '旧的"单位标定"必须删干净')
```

- 第一条**把错误公式本身写成了断言** —— 代码越错越"通过"；真去修符号反而会让自测变红。
- 第二条还**强制删掉了上一版"用掩码内容框逐轴自标定"的做法**（`unitMapper`）。那个做法虽然是启发式，
  但它是**逐轴线性拟合**：拿顶点并集拟合掩码实测内容框，**会自然得到负斜率的 Y** —— 也就是说它本来能自动搞对符号。
- `hitPart()` **从未在测试里被执行过**。
- `PET_ZONE_DEBUG` 那套"框中心命中自检"（`pet.js:564-573`）用**同一套错误变换**反解框中心，
  属于同义反复、必然自证 —— 这就是 8 个提交原地打转的机制性原因。

⇒ 净效果：**一个能自校准的实现，被换成了一个系数错 + 符号错的实现，并且用源码正则把它锁死。**

### 修复建议

**不要再手写换算**，直接用库的权威函数：

```js
const verts = state.model?.internalModel?.getDrawableVertices?.(index)   // raw*PPU + 画布中心，Y 已取负
```

若坚持自己算，必须是 `x = rawX*ppu + originalWidth/2`、`y = -rawY*ppu + originalHeight/2`
（`ppu = internalModel.pixelsPerUnit`，或 `coreModel.getModel().canvasinfo.PixelsPerUnit`）。

**注意连带影响**：修好符号后，`PART_ZONES` 的现有映射会失效（`Part29 → head` 是镜像下的产物，
真实的"头顶"应是 `Part7 头饰` 一带），必须**重新按正确坐标配一遍**，并同步改掉
`live2d.js:477-486` 的注释、`check-plugin.mjs:2087-2091` 的反面断言、以及交接文档里的错误结论。

**必须改测试**：把 2109 那种"源码正则断言"换成行为断言 ——
例如"在真实模型上，所有部件包围盒的并集必须 ≈ 掩码实测内容框（误差 < 2%）"，
或喂一组已知 `canvasinfo` + 已知 raw 顶点断言换算结果。否则修完还会被测试反咬。

## 3. 【P0·已证实·**已修复 2026-10-05**】`safePreview` 没有修好它声称修好的诊断

- 代码：`packages/pet-plugin/index.js`（原 `:131-147` 的 `safePreview`），注释 `:126-130` 与 `README.md:586` 都声称

- 真因不是循环引用，而是载荷里的 `agent` 是 **Cordis context 代理**，`JSON.stringify` 读 `toJSON` 时被 Proxy 的 inject 校验抛错。

### 修复（`CODE_REVISION` 24 → 25）

- 新增 `sanitizeForPreview()`：**不走 `JSON.stringify` 的隐式取值**，而是自己逐属性枚举 +
  **逐个 `try/catch`**，读不到的属性就地标 `<读取失败: …>`，绝不因一个坏属性丢掉整条预览；
  枚举本身被代理拒绝时退化成 `<无法枚举: …>`。`safePreview()` 改为"先清洗、再 stringify"，
  保留 JSON 形态便于肉眼比对。
- **更关键的是修测试**：原来那条「回归：循环引用载荷的预览仍可读」用的是**普通对象造循环** ——
  比真实宿主**宽松**，所以它一直绿。新增一条用**会抛的 `Proxy`**（读非 `session` 属性即抛
  `cannot get property "…" without inject`）的回归测试，才复现得了真机。

### 追加改动（同一轮，用户看过候选图后定的）

**「点头顶 → 惊喜」被否掉，换成 ⑤「舒服得眯起眼 + 轻轻歪头」。**

用户原话："惊喜的效果并不适配摸头顶"。我先渲染了 10 个候选（`.audit/cand-face.png` /
`cand-head.png`）实测对比，过程中查清了这个模型的**表情实现机制**——很值得记：

- 这个模型 13 个"表情"文件里**只有一行** `ParamX=1/Add`，全是**开关**，不是逐参数调脸。
- 真正的切换机制是**按参数键控的 ArtMesh 不透明度**：例如 `spiral`(`Param2=1`) 会
  打开 `Part13「白眼」`（画层 34/35）、同时关掉 `Part14 左眼`/`Part16 右眼`/`Part15`/`Part17`。
  所以"换表情"= **换一套画好的眼睛素材**。
- 因此**连续参数**才是手搓表情的正路，而实测：`ParamMouthForm` **默认就是 1**（她平时已在微笑）、
  `ParamEyeLSmile/RSmile` 单独开**几乎无效**、真正管用的是 `ParamEyeLOpen/ROpen`（眼睑开合）。

选定的 `HEAD_PAT`（`motion-policy.js`）：`ParamEyeLOpen/ROpen` 向 `0.25` **混合**、
`ParamEyeLSmile/RSmile` 向 1 混合、`ParamAngleZ` **叠加** `-16°`、`ParamBodyAngleZ` **叠加** `-7°`。

> **用户看过实机后又提了两条**（原话）："歪的幅度太小，而且没有过渡，起码我没感受到过渡"。
> 于是本版：① 幅度 `-8°` → **`-16°`**，并加身体一起倾（像"靠过来"）；
> ② 从"瞬间贴上、到点瞬间撤掉"改成**缓动包络** ——
> `riseMs 420 / holdMs 700 / fallMs 620`（共 1740ms），起回两段都用 `easeInOutCubic`。
>
> ⚠️ **这里有个反直觉的坑**：第一版我用了 `easeOutCubic`（快起慢停），数学上"有缓动"，
> 但它 **80ms 就走完 58%** —— 看上去仍然是"啪一下贴上去"。**"有缓动"不等于"看得出过渡"**，
> 要看的是**起步段的速度**。所以改成两头慢，并把上升段从 320ms 拉到 420ms。
> 现在自测直接锁这一条：上升段 1/4 时间处的包络必须 `< 0.2`（用 easeOut 会到 0.58）。
>
> 另一条关键性质：**t=0 时一个字都不写**，到点后**停止写入**（让动作/眨眼自然接管），
> 这样才没有"贴上去/撤下来"的硬边。逐帧验证见 `.audit/pat-filmstrip.png`
> （t=0 不动 → 160 微眯 → 320 近峰 → 500~1150 保持 → 1450 基本回正 → 1740 复原，12 帧）。

> ⚠️ **叠加 vs 覆盖这条必须记牢**：待机动作 `Scene4`（180s）每帧都在写 `ParamAngleZ` /
> `ParamEyeLOpen` / `ParamBodyAngleZ` —— 对动作驱动的参数**覆盖 = 把动作停了**
> （`live2d.js` 的 `stepFlick` 注释早就记过这个坑）。所以歪头/身体倾用 `{add}`、眯眼用 `{to}` 混合，
> 并且覆盖层必须排在 `applyBlink()` **之后**（否则眨眼接管会把压到 0.25 的眼睑顶回去）。

新增自测（121 → **122 项**）：包络形状（0→1→0、单调、中点 0.5、**起步平缓**）、
`{to}`/`{add}` 语义与包络缩放、t=0 不写值、时长自洽、**幅度下限 ≥12°**、
"动作驱动的参数必须用 `{add}`"、"覆盖必须在眨眼之后"、"不许再用 setTimeout 硬撤"。
